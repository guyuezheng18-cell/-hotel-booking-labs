# 酒店预订系统功能与模块划分

版本：V0.2（按审阅意见修订）

日期：2026-11-11

需求依据：实验一 requirements.md V1.6，REQ-001 至 REQ-023。

用途：为实验二的软件架构、UML和UI设计提供统一的功能边界与需求对应关系。

## 一 项目范围与主要功能

系统面向国内多家酒店，提供顾客查房与预订、酒店工作人员维护房源与处理订单、平台管理员管理酒店和账号及协调履约异常的功能。一次订单预订一种房型的一间房，可连续住宿多晚，采用北京时间、人民币、到店付款和系统内通知。

业务主线为：查询房源 → 提交预订并预留库存 → 酒店确认 → 办理入住 → 实际退房完成。围绕这条主线，系统还支持修改和取消预订、确认超时取消、未到店取消、提前退房、履约异常协调，以及统计和操作追溯。

第一版不包含线上支付、自动退款、延迟费用计算、具体房号选择、优惠券、会员积分、评价、短信验证码或第三方登录。延住另建后续日期订单，仍须经过预订与酒店确认，不直接延长原订单。

实验一REQ-022中的“仅完成需求分析”描述的是实验一交付阶段；实验二在相同业务范围内推进软件设计与建模。

## 二 角色与操作范围

| 角色 | 主要操作 | 数据和权限边界 |
|---|---|---|
| 顾客 | 自行注册、登录退出、查询房源、预订、查看和合规修改或取消自己的订单、查看通知 | 只能读取或操作自己的订单和通知；不能自行取得工作人员或管理员身份 |
| 酒店工作人员 | 维护酒店资料、房型、逐日库存房价及停售状态；确认、拒绝、办理入住退房；处理履约异常；查询统计和日志 | 账号由管理员创建并绑定酒店，业务数据限所属酒店；订单操作须满足状态、时间和原因记录要求 |
| 平台管理员 | 管理酒店、账号和权限；查询异常相关订单，通知并联系顾客、记录协调情况；查询全部日志 | 协调权限不包含直接确认、拒绝、取消订单，也不替代所属工作人员办理入住退房 |

定时任务是系统内部执行机制，用于触发确认超时、未到店取消及延迟退房提醒，不增加第四种人工用户角色。

## 三 功能模块划分

按业务职责划分为10个逻辑模块。三个角色端共用模块提供的业务能力；一个模块可以包含多个页面，一个页面也可以组合多个模块的信息。模块划分不要求分别部署，具体层次、类和存储技术留到架构设计阶段确定。

| 编号 | 模块名称 | 主要功能 | 主要需求 |
|---|---|---|---|
| M01 | 账号与权限管理 | 顾客注册，登录退出，工作人员账号创建与酒店绑定，账号停用，角色及数据范围校验，登录失败暂停 | REQ-001、002、020 |
| M02 | 酒店与房型管理 | 管理多家酒店及停用状态，维护名称、城市、地址、电话；维护所属房型的名称、床型、人数上限 | REQ-003、004 |
| M03 | 库存与房价管理 | 按房型和日期维护总数、价格、停售状态；查询逐日余量；统一处理逐晚占用、复用与释放 | REQ-005、008 |
| M04 | 房源查询 | 按城市、酒店、日期、人数、房型、住宿总价组合筛选，展示逐晚价格、总价、区间可售余房，按总价排序 | REQ-006、019 |
| M05 | 预订与订单管理 | 创建订单及快照，查询详情和历史，改订，顾客取消，酒店确认拒绝，统一状态变更、版本检查和重复请求处理，确认超时取消 | REQ-007、009、010、011、012、016 |
| M06 | 入住与退房管理 | 核对并办理入住，未到店处理，正常与提前退房，延迟退房提醒及实际离店记录，支持衔接延住新预订 | REQ-013、014 |
| M07 | 履约异常处理 | 确定受影响房型日期，组织停售、筛选受影响订单，记录无法履约原因和沟通情况，按状态协调处理 | REQ-015 |
| M08 | 系统内通知 | 保存订单处理结果、发生时间及必要原因，顾客查看自己的历史通知并进入订单详情 | REQ-023 |
| M09 | 订单与余房统计 | 本酒店各状态订单数、每日余房、预订金额及其计算口径说明 | REQ-017 |
| M10 | 操作日志与追溯 | 记录关键操作的操作者、时间、对象、前后值、结果与原因；按时间、操作者、订单号查询 | REQ-018 |

### M01 账号与权限管理

每次业务请求都校验当前身份、账号是否停用、角色和数据归属，不能只靠隐藏页面按钮控制权限。退出使本次登录失效；停用使账号全部登录状态失效，保留已有订单和历史。

10分钟内连续输错密码达到5次，自第5次失败起暂停密码登录10分钟，暂停期间正确密码也不能登录；成功登录或暂停结束后清零计数。密码存储和隐私保护是本模块与所有业务输出的共同约束。

### M02 酒店与房型管理

本模块维护当前酒店和房型资料，供查询、预订及库存维护使用。酒店停用后保留历史关联，不直接删除已有订单。订单中的酒店、房型信息由M05保存快照，当前资料修改不能覆盖历史订单。

### M03 库存与房价管理

逐日余量等于总数减去仍占用数量，库存总数不得低于当前占用。库存记录按“房型＋日期”唯一。

占用区间为入住日到退房日前一晚；待确认即占用，酒店确认和办理入住不重复扣减。逐晚记录区分预留、已使用、已释放，取消或退房只释放符合规则且仍占用的日期，重复操作不能再次释放。释放不会清除停售，也不能让过去日期重新可售。

本模块提供库存操作能力，由M05协调订单与库存的整体提交，不把更新库存和更新订单拆成互不关联的成功结果。

### M04 房源查询

可按名称搜索本市酒店，默认查询全部酒店。选定酒店后按其标识与其余条件组合筛选。查询只展示候选房源，不预留房间。整段住宿每晚均可售才返回可订结果，区间可售余房取各晚余量的最小值，例如5、1、3间显示1间；总价为各晚价格之和。提交预订时M05仍需调用M03复核库存与报价。

### M05 预订与订单管理

本模块是订单状态和预订方案的统一管理入口，保存订单号、顾客及酒店房型关联、住宿区间、人数及联系人、逐晚价格与资料快照、确认截止、实际入住退房时间及修改历史。

采用待确认、已确认、已拒绝、已取消、已入住、已完成六种状态，禁止未定义的转换和终态恢复。M06、M07和定时任务通过本模块执行受约束的状态操作。

关键规则如下：

- 同次预订请求重发返回原订单及当前状态，即使原订单已取消，也不能重新生成订单。同一顾客、酒店、房型和完全相同住宿区间最多存在一笔待确认、已确认或已入住订单。
- 有效确认截止为“当前方案成功提交时间＋30分钟”与“入住日次日00:00”较早者；到达截止后禁止人工确认或拒绝，统一按超时取消处理，并在一分钟内完成取消和通知。
- 修改须在原入住日00:00之前，修改后的入住日须晚于修改当日。改房型或日期需新旧方案对照、重新报价与主动确认，成功后回到待确认、重算截止并整体更新库存；同房型同日期可复用原预留。失败保留原方案；新方案后来被拒绝或超时不恢复旧方案。
- 仅修改人数或联系方式仍须校验权限、状态、时间及信息有效性，但不改变价格、库存、状态或截止，也不因后来改价、停售、可售余量为零而拒绝。
- 顾客可在当前方案确认截止前取消自己的待确认订单；已确认订单仅可在入住日00:00之前取消。执行前展示订单信息和不可恢复提示，取得主动确认，最终提交重新校验。

### M06 入住与退房管理

工作人员只可为本酒店已确认订单在入住日14:00起、次日00:00前办理入住。到次日00:00仍未入住时，触发M05按“未到店”取消，并在一分钟内完成通知；到达截止即禁止入住，不等待定时任务刷新页面状态。

正常退房应在预订退房日12:00前办理。提前退房仅释放实际退房日当晚及以后原订单仍占用的库存，保留已住晚数、原预订日期和价格。超过12:00未实际离店时仍为已入住并提醒工作人员；实际离店后才能完成订单，并记录延迟原因。延住通过M04、M05另行预订。

### M07 履约异常处理

工作人员先通过M03停售受影响房型日期，再通过M05查找受影响订单，记录原因及沟通情况。截止前的待确认订单由所属工作人员拒绝，已超时的待确认订单按超时规则处理；已确认订单记录无法履约原因和沟通情况后由所属工作人员取消；已入住订单人工协调，不能直接取消或虚假完成。

管理员可以查询、通知、联系与协调，不能直接执行订单状态操作，也不能以管理员身份代替工作人员停售。异常模块组织流程，库存修改由M03承担，订单状态变化由M05承担，释放后继续保持停售。

### M08 系统内通知

酒店确认、酒店拒绝、顾客取消、确认超时取消、未到店取消和无法履约取消成功后，保存对应通知；业务失败不得产生成功通知，重复请求未产生新状态变化时不重复生成结果通知。

通知保存事件发生时的结果，订单详情显示当前状态。顾客离线不影响保存和时限；只能查看自己的通知。M07的异常联系、通知和沟通记录不能冒充尚未成功的订单处理结果。

### M09 订单与余房统计

订单数和预订金额按订单保存的预订入住日期筛选；每日余房按库存日期统计。预订金额仅纳入已确认、已入住和已完成订单的当前方案价格快照，明确注明“不代表实际收款”；提前退房不重算预订总价。余房展示保留停售标记，不能仅凭数量判断可订。

### M10 操作日志与追溯

记录房价库存、订单方案与状态、账号权限、履约异常等关键变更。成功日志需与业务、库存及订单版本一致；失败不能记为成功，自动操作标明系统与具体原因。工作人员查本酒店日志，管理员查全部，顾客通过订单和通知了解处理结果。日志不包含原密码，至少保留至课程结束，不开放任意修改删除入口。

## 四 模块协作边界

| 场景 | 主要协作 | 整体结果 |
|---|---|---|
| 顾客提交预订 | M01校验身份 → M05检查请求与方案 → M02核对资料、M03复核逐晚库存报价 → M05保存订单和快照、M03预留 → M10记录 | 订单与全部住宿日期库存一起成功或一起不生效；查询不占库存 |
| 顾客改房型或日期 | M05展示新旧方案、取得确认 → M03计入可复用预留并检查新方案 → M05与M03整体更新 → M10记录 | 成功生成新版本并重算截止；旧超时任务不能影响新版本，失败保持原方案 |
| 确认、拒绝或取消 | M01校验范围 → M05校验当前状态、版本和时间 → 按需调用M03释放 → M08保存通知、M10记录 | 确认不重复占用；拒绝取消只释放一次，保留停售和历史 |
| 入住与退房 | M06核对实际到离店 → M05执行合法状态转换 → 按需调用M03释放 → M10记录 | 入住不重复扣减；提前退房仅释放未使用部分，延迟未离店保持已入住 |
| 履约异常 | M07组织工作人员调用M03停售 → M05筛选和处理订单 → M07留沟通记录 → M08保存成功处理结果、M10留痕 | 管理员参与协调，订单状态操作由所属工作人员执行 |
| 统计与追溯 | M01校验范围 → M09读取M05、M03数据；M10提供受权日志查询 | 统一数据口径，统计和日志查询不直接修改业务数据 |

数据持久化、事务、唯一性约束及任务调度属于公共技术支撑。后续架构设计应让订单、逐晚库存、成功日志及对应结果通知保持一致，保证应用中断后的恢复和请求重试，不要求每个功能模块独立使用数据库或服务。

## 六 划分理由与界面衔接

酒店与房型同属房源基础资料，合并管理；逐日库存房价涉及并发和全区间一致性，单独管理。查询只读取候选房源，订单负责最终复核及成交结果。入住退房、履约异常有独立工作流程和操作界面，但共用订单状态与库存规则，避免形成多套修改逻辑。

通知面向顾客展示处理结果，日志面向后台追溯操作，访问范围和信息粒度不同，分别设模块。统计独立提供只读口径，避免把预订金额误作实际收入。账号权限作为共同入口约束所有业务。

| 界面入口 | 后续UI需覆盖的页面或区域 |
|---|---|
| 公共入口 | 注册、登录、错误与暂停提示、退出 |
| 顾客端 | 房源筛选结果和详情、预订确认、我的订单与详情、改订对照确认、取消确认、通知列表与详情 |
| 酒店工作人员端 | 酒店资料、房型列表编辑、库存房价日历及停售、订单筛选与确认拒绝、入住退房、异常处理及沟通记录、统计、日志查询 |
| 平台管理员端 | 酒店管理、账号与角色及酒店绑定、异常订单查询和协调、全局日志查询 |

以上为第一步设计初稿。后续根据学生实际审查意见修订，再据此确定架构和绘制UML。
