版本：V0.1（AI辅助设计稿，待学生审查）  
日期：2026-11-09  
依据：实验一 requirements.md V1.5、实验二 01-功能与模块划分.md。  
范围：明确部署、分层、模块调用、数据持久化及关键一致性机制，为后续UML与原型实现提供依据。

## 一 总体架构与选型

采用浏览器与服务器架构（B/S）。顾客、酒店工作人员和平台管理员通过浏览器访问同一套Web应用，应用内部按职责分层、按业务划分10个模块，共用一个关系数据库。前端页面负责展示与输入，后端负责权限及业务校验，数据库保存业务结果。

这是一个按模块组织的单体应用。模块有独立职责和调用接口，但跨模块的业务变更可以使用同一个数据库事务，适合本课程的原型规模和订单库存一致性要求。

建议的后续实现组合为Python、Flask、服务端HTML模板与少量JavaScript、PostgreSQL。Flask提供Web请求及模板入口；PostgreSQL承担关系约束、事务和并发控制。此处为设计选择，本轮不安装依赖、不编写业务原型，也不固定软件版本。实际实现前再记录所用版本。

部署时，Web进程和一个独立的定时任务工作进程使用同一套业务代码并连接同一数据库。课程测试可将应用和数据库放在同一台机器。工作进程不接受用户请求，仅扫描应处理的数据并调用业务服务；不会形成另一套订单规则。

```text
顾客浏览器       酒店工作人员浏览器       平台管理员浏览器
      \                 |                 /
              页面与请求入口
                     ↓
       业务服务与领域规则（M01—M10） ← 定时任务工作进程
                     ↓
           数据访问与事务管理
                     ↓
              PostgreSQL数据库
```

HTTP用于本机开发，实际通过网络提供服务时使用HTTPS。浏览器不能直接连接数据库，三个角色端也不分别维护订单或库存副本。

## 二 分层职责与调用约束

| 层次 | 职责 | 不应承担的工作 |
|---|---|---|
| 表现层 | 页面、表单、列表和确认提示；接收请求；基本格式校验；调用服务；返回页面或数据 | 不直接改库存，不自行判断最终权限或订单状态 |
| 业务层 | 当前身份及数据范围校验、预订报价、状态转换、库存规则、事务协调、通知与日志内容 | 不把数据库连接或SQL暴露给页面 |
| 数据访问层 | 通过Repository接口进行查询、锁定、写入；提供事务上下文；落实数据库约束 | 不绕过业务服务替用户确认、取消或改订 |
| 数据存储 | 持久保存账号、房源、订单与历史、库存、通知、日志及任务依据 | 不依赖应用内存作为唯一业务记录 |

业务层内部区分两类职责：应用服务组织一次操作的步骤和事务；领域对象与规则校验器判断状态、时间、人数、库存区间等规则。例如OrderService协调改订，Order及对应规则校验器判断能否修改，InventoryService负责逐晚占用变更。

页面请求沿“表现层 → 业务层 → 数据访问层 → 数据库”执行。定时任务从业务层进入。业务模块通过服务方法协作，不能直接修改其他模块的表。跨模块调用共享同一事务上下文，不允许内层服务提前独立提交。

## 三 十个模块在架构中的位置

| 模块 | 业务服务 | 依赖及责任边界 |
|---|---|---|
| M01 账号与权限 | AuthService、AccessPolicy | 提供当前用户、角色、所属酒店及授权判断；所有入口调用；业务服务继续核对对象归属 |
| M02 酒店与房型 | CatalogService | 管理当前酒店、房型资料，向M04/M05提供有效资料及人数上限 |
| M03 库存与房价 | InventoryService | 提供逐晚价格、可售性、占用、复用和释放；维护库存与价格时同样遵守加锁规则 |
| M04 房源查询 | SearchService | 通过M02/M03的查询接口组合房源、计算总价和区间最小余房；查询不占用库存 |
| M05 预订与订单 | OrderService、OrderPolicy | 统一状态、版本和方案变更；调用M02/M03，组织M08/M10写入，是订单操作的事务协调入口 |
| M06 入住与退房 | StayService | 核对实际到离店及对应时限，调用M05的入住、未到店、退房命令；不自行写订单表 |
| M07 履约异常 | IncidentService | 组织停售、受影响订单查询、联系沟通；经授权调用M03及M05，记录异常信息 |
| M08 系统内通知 | NotificationService | 由已成功的业务变更构造通知，在同一事务中保存；提供顾客本人通知查询 |
| M09 订单与余房统计 | StatisticsService | 使用M05/M03的只读查询接口，在一致的查询快照中生成统计和明细 |
| M10 操作日志 | AuditService | 接收各业务服务给出的事件和前后值；成功日志参加原业务事务；受权提供查询 |

M05不反向调用M06或M07；由M06/M07发起调用，以避免循环。M05中的规则对人工和系统操作均生效。M08/M10写入过程不再回调订单变更。M01提供通用授权能力，不依赖订单模块；具体订单归属由调用方结合当前用户判断。

M07可将“停售受影响日期”作为一个先行事务提交，随后逐笔处理订单，每笔各自保持订单、库存、日志、通知一致。多笔异常订单不要求一次全部取消；处理中断后，停售仍保留，可根据已处理记录继续协调。管理员只能查询、通知、联系和记录协调，不能以调用M07为由取得停售或订单状态操作权限。

## 四 持久化数据设计

以下为逻辑数据结构，后续类图和数据库设计可细化字段。外键保留历史关联，酒店、房型和账号不通过级联删除清除已有订单。

| 数据结构 | 关键内容与约束 | 所属模块 |
|---|---|---|
| users | 唯一登录名、密码派生值及参数、角色、工作人员所属酒店、停用状态、登录暂停截止 | M01 |
| sessions、login_failures | 服务端会话凭据摘要及撤销信息；登录失败时间记录 | M01 |
| hotels、room_types | 酒店资料和状态；所属房型、床型、人数上限 | M02 |
| daily_inventory | 房型、住宿日期、总数、仍占用数量、当晚价格、停售标记；房型与日期唯一 | M03 |
| orders | 唯一订单号、顾客/酒店/房型、当前方案、六种状态、内容版本、确认截止、实际到离店时间、处理原因 | M05 |
| order_revisions | 每次预订方案及其资料和价格快照、人数、联系人、总价、方案编号，保留改订前内容 | M05 |
| order_nights | 订单方案、房型、住宿日期、当晚价格；每个方案日期唯一，保留原逐晚明细 | M05 |
| inventory_allocations | 关联订单方案、逐晚明细和日库存；记录预留、已使用、已释放及相应时间、释放原因 | M03 |
| operation_requests | 用户、操作类型、请求键、请求内容摘要、关联订单和处理事件；三者组成唯一请求标识 | M05 |
| order_events | 订单每次成功变更、前后状态、内容版本、原因和操作者，标识实际发生的业务事件 | M05 |
| notifications | 接收人、订单、业务事件、结果及原因、发生时间；同一事件同一接收人唯一 | M08 |
| incidents、incident_contacts | 受影响酒店房型日期、原因、处理进度、关联订单及沟通记录 | M07 |
| audit_logs | 操作者、所属酒店、对象、操作、必要前后值、时间、成功或失败及原因 | M10 |
| task_marks | 超时提醒等已处理标记，按任务类型、订单和方案编号唯一 | 公共调度 |

统计结果由业务数据计算，不另维护可被独立编辑的金额或库存副本。

价格以定点金额保存，入住退房日和库存日期使用日期类型；操作时间、确认截止和实际到离店时间使用带时区时间戳，业务日界线统一按Asia/Shanghai解释。价格大于零且最多两位小数，必须在入库前拒绝非法精度，不能靠数据库自动舍入代替输入校验。

日库存满足“0 ≤ 仍占用数量 ≤ 总数”，人数和总数执行整数范围校验。日库存计数与逐晚占用记录在同一事务内修改；保留的已使用记录不会因订单完成而被统一清零，不凭订单当前状态反推全部历史库存。

在orders上，为待确认、已确认、已入住状态建立以“顾客、酒店、房型、入住日、退房日”为键的条件唯一索引，落实有效预订唯一性。终态不再占用此唯一键，但原请求记录仍保留，重发原请求仍返回原单。

## 五 事务 并发与报价确认

### 创建预订

1. 校验当前会话及顾客身份，按“用户＋操作类型＋请求键”检查已成功处理记录。已处理则返回原订单及其当前状态，不再次占用库存；相同请求键携带不同内容时拒绝复用。
2. 开启事务，通过唯一请求标识协调并发重发；并发请求等待首次处理提交后读取原结果。失败事务回滚，不留下半成品请求占用。
3. 读取并保护本次校验所需的酒店、房型资料，防止校验期间酒店停用或人数上限变化导致使用过期条件；锁定全部住宿日期库存行，统一按房型ID和日期排序。缺少任一晚数据、停售或无房即整体失败。
4. 在锁内复核人数、当前业务日期、有效预订唯一性和逐晚报价。使用后端生成且绑定顾客、方案、逐晚报价的确认凭据，不能信任浏览器自行提交的价格。价格变化则回滚并展示新报价，由顾客再次主动确认后重新提交。
5. 保存订单及方案快照、逐晚明细、完整区间的占用、请求关联和成功操作记录。首次下单不凭空生成“酒店已确认”通知。
6. 全部提交成功后才返回成功。任一步失败全部回滚；提交成功但响应丢失时，重发原请求返回已保存的订单。

每笔只占一间房。锁住最后一间房的库存行后，后来的请求须等待并检查更新后的余量，所以不能依赖“先查到有房”或按钮禁用来防止超卖。

### 改订和一般订单操作

对已有订单先锁定订单行，再按统一顺序锁定涉及的库存行；所有流程避免持有库存锁后再反向请求订单锁。修改当前房价、库存及停售也锁定相同日库存行。必要的酒店房型资料锁先于订单与库存获取，各类流程保持一致顺序；数据库检测到死锁或锁等待超限时整笔回滚，按原请求标识有限重试或提示用户重试。

房型日期改订时，对旧区间与新区间所需库存的并集加锁，计算净变更。新方案可用余量可计入本订单同房型同日期原预留。新旧快照、占用、当前方案、状态、截止和日志一起提交；不能先释放旧房，再用独立事务抢新房。

仅修改人数或联系方式走独立命令，只检查对应信息、权限、订单状态和时间，不调用新方案可售性或重新报价校验，不改变库存、状态、价格和确认截止。

顾客取消和改房型日期在页面展示必要信息并取得主动确认；最终命令仍以数据库中的当前数据判断。页面提交预期内容版本，锁内对照当前版本；页面过期时返回冲突并刷新信息，不覆盖酒店已处理的结果。

所有状态变更递增content_version；仅房型或日期方案变化递增plan_revision，并重算确认截止。联系人变更只更新内容版本。这样既能发现旧页面，也不会因修改电话号码而让当前方案的超时任务失效。

确认、拒绝、取消、入住、退房在同一订单锁下校验当前状态、角色、时间和版本。时间判断使用取得锁后的可信当前时刻，不能使用打开页面时刻，也不能使用长事务开始时冻结的时间值。已到确认截止不再接受人工确认或拒绝，已到未到店截止不再接受入住。

### 日志 通知与回滚

发生确认、拒绝或规定的取消事件时，订单、占用释放、order_events、对应通知和成功日志使用同一事务提交。通知是数据库中的站内记录，不通过网络发送，因此不引入跨系统投递事务；顾客离线也能立即持久保存结果。

通知事件唯一性与请求幂等分别控制：请求未产生新状态变化时，不新建业务事件和结果通知。确认通知保留当时的结果，后来取消时增加取消通知，不覆盖旧通知。

业务失败先回滚，再在独立的短事务中尽力保存失败日志，不把失败日志和被回滚业务误作成功记录。数据库不可用时记录运行错误并反馈失败，不返回业务成功。密码、原会话凭据不得写入日志。

## 六 定时任务与恢复

独立工作进程每10秒扫描到期数据，任务依据以数据库中的当前方案和截止时间为准。业务校验不依赖扫描是否及时执行。

| 任务 | 触发条件 | 处理方式 |
|---|---|---|
| 确认超时 | 待确认且当前方案确认截止已到 | 调用M05，锁定后复核方案与截止，按确认超时取消、释放对应占用、记录通知日志 |
| 未到店取消 | 已确认且入住日次日00:00已到 | 经M06调用M05，锁内复核未入住，按未到店取消并通知 |
| 延迟退房提醒 | 已入住且预订退房日12:00已到，尚无实际退房记录 | 按订单与方案保存一次提醒，工作人员在待办区域查看；保持已入住，不自动加夜或完成 |

扫描结果携带plan_revision。执行前发现方案变化、状态已处理或截止尚未到达则跳过；联系人修改不影响该方案定时处理。重复扫描或工作进程重启不重复释放、通知或提醒。多进程误启动时，数据库行锁和唯一事件/提醒标记仍避免重复生效。

按截止时间排序、分批扫描，并为应取消任务优先分配处理时间；10秒轮询只提供调度余量，不能直接证明满足一分钟。后续需实测扫描、锁等待、提交和通知保存的总耗时，确保确认超时及未到店在截止后60秒内完成；锁等待超时的任务应在剩余时限内优先重试，超出时限记为未达标。

应用重启后从数据库恢复，不用仅存于内存的倒计时。工作进程启动即补扫逾期数据，Web启动完成连接和必要检查后提供服务，不等待全量历史遍历。Web中断时独立工作进程可继续处理到期任务；工作进程自身重启时补扫。全部任务执行进程长时间停止会影响通知时限，不能以补扫替代原时限验收。

数据库及存储正常时，事务未提交的变更回滚；已提交结果、请求关联、通知和日志保留。按实验一要求开展“创建/修改/取消 × 写入前/写入中/提交后响应前 × 各2次”共18次中断恢复验证，每次从启动指令到正常查询及业务恢复不超过60秒，并重发原请求核对一致性。

## 七 安全 查询与统计

服务端保存可撤销会话；浏览器仅持随机登录凭据，不把角色和酒店归属作为可信输入。每次请求查询有效会话和账号当前状态、角色及所属酒店，退出撤销本次会话，停用撤销全部会话；旧页面不能继续使用原权限。

顾客查询始终附带customer_id，工作人员查询始终附带hotel_id，管理员仅在明确授权的管理或异常查询入口取得相应范围。订单详情、通知链接和日志查询都再次检查数据范围。修改酒店、角色、顾客ID等请求参数不能扩大权限。表单变更请求增加CSRF校验，使用参数化数据库访问，模板转义用户输入。

密码使用成熟密码派生库保存带盐哈希及必要参数，不自制加密。登录失败时间持久保存；同一账号登录判定串行更新，统计当前10分钟内连续失败，达到5次后从第5次起暂停10分钟；成功或暂停结束清零，暂停期间不因密码正确而放行。

房源查询对[入住日，退房日)逐晚数据进行筛选，要求记录完整、均未停售、余量均为正且人数合规；汇总总价并取最小余房。为酒店城市、房型所属酒店、房型日期唯一键、订单所属顾客、酒店入住日及状态、确认截止、通知接收人及时间、日志筛选条件设计必要索引。避免逐条订单或逐日查询，提供稳定分页及总价排序。

统计和对应明细使用同一筛选条件与一致的读快照；预订金额只含已确认、已入住、已完成，按当前方案价格快照计入，标明“不代表实际收款”。提前退房释放库存但不重算预订总价。

REQ-019的目标仍是在4核8GB环境下，100家酒店、每家5种房型、180天库存和1万订单，20并发共100次查询，至少95次正确且不超过2秒，超过5秒按超时计。索引与批量查询是实现手段，本阶段不声称已通过测试。

## 八 设计取舍与后续UML

| 决策 | 原因与代价 |
|---|---|
| 单套应用按模块组织 | 部署和调试步骤少，跨模块可用本地事务；各模块须通过服务接口保持边界 |
| 页面由服务器提供并辅以少量脚本 | 满足表单、列表、确认和管理台需求，原型易于实现；复杂交互日后再扩展 |
| 共用关系数据库 | 关联、唯一性、历史和多表事务直接支撑需求；查询与加锁仍须规范设计 |
| 订单统一管理状态，库存统一管理占用 | 正常、异常、人工、自动处理共用规则；服务入口须明确区分权限和业务原因 |
| 通知日志与成功业务同步保存 | 避免订单成功而通知日志丢失；写入失败会使整笔业务回滚 |
| 工作进程周期补扫数据库 | 重启后可继续处理当前方案；须监测积压并实测一分钟时限 |
